# Execution parameter and optimizer candidate binding checkpoint

2026-10-24 backend source checkpoint. No retained numerical engine, generator or scoring algorithm changed. No Tauri/app window was launched and review PID 22812 was not targeted.

## Ordinary execution

`execution_inputs.rs` now checks ordinary overrides against the actual approved reflected strategy schema before SDK/runner dispatch. It accepts reflected property names and display aliases with the existing ASCII case-insensitive convention, rejects unknown/environment properties and duplicate aliases targeting one property, and bounds collections to 256 entries, names to 256 bytes and values to 2048 bytes. NUL values fail before process dispatch.

The original C# runner deliberately records unrecognized inputs and can still exit zero. `ReportWriter.WriteJson` always writes `parameter_unknown`, using an empty array when no parameter file/override result exists. Native report parsing now requires that field to be a string array and empty before mapping metrics, capturing a report digest or publishing last-good. Missing, null, malformed or nonempty records fail instead of silently presenting an ignored override as applied. Complete synthetic fixtures were updated to the actual writer contract; sparse comparator fixtures remain rejected.

Date validation now parses each nonblank endpoint independently through the existing UTC parser, and compares a valid pair with start strictly before the exclusive end. The original CLI's Int32 replay-count domain is enforced before dispatch, including zero as unlimited. Negative finite commission values retain the original C# profile-rate sentinel semantics.

## Optimizer evidence

The prior adapter checked report/preset paths and strategy/symbol but never read preset contents or bound candidate rows to the generator. A synthetic test even supplied an empty preset and an arbitrary folder hash as completed output. That acceptance path is removed.

The small `CandidateBindings.cs` managed-host adapter calls the **unchanged original** `OptimizerConfig.Load`, `CandidateGenerator.Generate`, `ParameterValue.ToString` and `Program.JsonOptions`. It captures identities before invoking original Main, rechecks native frozen config/base/data/profile hashes afterward, records actual report/candidate/replay-preset byte digests, writes a bounded receipt and prints exactly one SHA-256 stdout marker. It preserves original candidate generation, seeded randomness, System.Text.Json escaping, G17 formatting, scoring and exit codes. It supports only this app's exposed single-scenario input surface; it does not claim all original CLI features.

Rust authenticates the exact receipt bytes against that one trusted process marker and the hashes captured by native preparation before launch. It then checks candidate id/hash and original parameter text against the receipt, reads bounded candidate and replay presets, validates their chart and complete parameter merge against the frozen base plus original typed candidate values, and verifies the report's actual parameter-file path, empty unknown list and applied-count contract. The retained `parameter_overrides` property is a **count**: preset entries plus the candidate CLI overrides applied again by the original runner; it is not a map of values. Actual source metrics and nullable profit factor stay separate from optimizer score inputs.

Missing/malformed/duplicate markers, changed receipt or artifact bytes, foreign candidate identities, mismatched values/counts and unknown preset fields leave completed-looking rows **unproven with unavailable metrics**. Genuine failed rows remain failed. Interrupted work cannot gain completed authority from an unauthenticated receipt file. No candidate is automatically recommended or promoted.

`prepare-optimizer.ps1` includes the new helper in the production wrapper assembly. The explicit lifecycle-only fixture supplies a nonshipped no-op binding dependency, emits no receipt marker and proves only process containment/exit codes. It is not optimizer or economics evidence.

## Later ownership-cleanup correction

A read-only review found that execution exposed `running = false` before removing its old cancellation sender. A new execution could install a sender in that gap, then have the previous guard remove it. Build exposed its busy latch before cancellation cleanup and approval publication, allowing the equivalent overlap and a stale approval overwrite.

The lead authorized only these lifecycle hunks. `ExecutionGuard` now clears cancellation before releasing the running latch. The workspace build command retains a dedicated RAII guard through successful-build approval; its destructor clears the old sender and releases busy last, including preparation and approval failures. The private source manifest and existing engine behavior are preserved.

Two new synchronization-only tests, `execution_lifecycle_tests.rs` and `workspace_build_lifecycle_tests.rs`, hold the busy mutex while waiting for cancellation-sender removal. The previous reversed cleanup order times out; the corrected order removes the sender while the job remains busy. These tests launch no compiler, engine, provider or native UI. Rust formatting/parsing passed; actual test results remain pending in the execution owner's coordinated batch (`--lib lifecycle_tests`).

The separate compiler source-membership finding was handed to that owner: locking existing source files cannot prevent a new wildcard-matched `.cs` file from entering compilation. The proposed app-generated MSBuild hook pins the exact manifest source list at `CoreCompile`, distinguishes SDK-generated source files, and leaves retained projects unchanged. The lead authorized new `execution_process.rs` and its focused test module. The new module reuses that one parent-owned Job Object implementation. It forwards the original frozen DLL and CLI vector unchanged after a fixed host delimiter, inherits the existing environment, captures each stream at no more than 128 KiB plus one overflow-detection byte, and preserves original nonzero exit statuses.
